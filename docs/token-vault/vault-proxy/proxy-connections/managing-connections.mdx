Proxy connections can be created and managed via our Portal or our API. We recommend using our Portal, which allows you to configure them step by step and test them before creating them. However, our API may be more efficient if you want to create many connections at once and if you have prepared a JSON object for your connections.

## Step 1: Create a new connection

Navigate to **Token vault > Proxy connections** in your Portal and click on **+ Create connection**. This option is only available to **Admin** users at the **Organization** level.

Choose a unique, simple but descriptive **name** for your connection and a **description** if needed. You can update the name and description at any time later.

<Note>
  This step is equivalent to the API endpoint [here](/reference/createvaultconnections#/) if you wish to use API to create a connection.

Similarly, the API endpoint to update a connection details can be found [here](/reference/updateconnection#/).

</Note>

Most importantly, in this step, you must define the connection **type**.

### How to choose the connection type

Is it an external system that initiates the connection? Then your connection is **Inbound**. An inbound connection can be configured for both when the external system sends sensitive data in the request to your system, or it requests to get sensitive data in the response from your system.

Is it your system that initiates the connection? Then your connection is **Outbound**. An outbound connection can be configured for both when you want to send sensitive data to an external system, or to request to get sensitive data in the response from an external system.

## Step 2: Create the first version of the connection

Once you create the connection, you will configure the first version of the connection. Connections has versioning so that you can create immutable versions, which allows you to make changes always on new versions without risking your version on live. When you're creating a new version of an existing connection, select **+ New version** to start with an empty configuration or select **Edit as new version** to duplicate an existing version to make your changes on. You can create as many versions as you want, but only one can be used on live at a time, which we call the **Live version**.

Regardless is inbound or outbound, any connection will have a URL to invoke this connection, and a URL to which the proxied message should be transmitted after.

<Note>
  This step is equivalent to the API endpoint
  [here](/reference/createvaultconnectionversions#/) in
  our API reference.
</Note>

### Configuring Inbound Connections

In an inbound connection, the 'Public URL' is an address that an external system can call to invoke this connection. This must be a unique URL that will be generated by Payrails or a custom URL that is defined by the merchant.

<Warning>
  Please make sure the third parties sending request to your system never sends
  any secret within the URL. If there is such an API contract by any third party
  you work with, please inform Payrails support to recommend the best setup.
</Warning>

Next, you will provide the 'Proxy URL' to which Payrails should send the proxied message.

<Tabs>
  <Tab title="Static Routing">
    ##### Static Routing in Inbound Proxy

    Static routing allows you to define a fixed mapping between a public URL and a proxy destination URL. Every request received on the public URL is forwarded to the same proxy URL, with no dynamic path extraction involved.

    ###### How It Works

    You define a public URL that Payrails exposes, and a proxy URL that the request will be forwarded to. The paths are fixed and do not change based on the incoming request.

    Your public URL is:

    ```URL
    https://proxy.payrails.com/payments/checkout
    ```

    Your proxy URL is:

    ```URL
    https://api.myservice.com/v1/payments/checkout
    ```

    The request received:

    ```URL
    https://proxy.payrails.com/payments/checkout
    ```

    The request forwarded:

    ```URL
    https://api.myservice.com/v1/payments/checkout
    ```

    In this example, every request hitting the public URL is forwarded as-is to the defined proxy destination — no parameters are extracted or substituted.

    ###### When to Use Static Routing

    Static routing is ideal when:

    * The destination endpoint is always the same regardless of the request.
    * You want a simple, predictable mapping with no variability in the path.
    * You are proxying a single, well-known endpoint such as a payment processor or webhook receiver.

  </Tab>

  <Tab title="Dynamic Routing">
    ##### Dynamic Routing in Inbound Proxy

    Dynamic routing allows you to forward path parameters from the public URL directly to the proxy destination URL. This enables flexible, templated routes where segments of the incoming request path are extracted and reused when forwarding the request.

    ###### How It Works

    You define named parameters by wrapping a path segment in curly braces `{}`. These parameters are extracted from the incoming request and injected into the proxy URL at the corresponding positions.

    Your public URL is:

    ```URL
    https://proxy.payrails.com/merchant/{merchantId}/order/{orderId}
    ```

    Your proxy URL is:

    ```URL
    https://api.myservice.com/clients/{merchantId}/orders/{orderId}
    ```

    The request received:

    ```URL
    https://proxy.payrails.com/merchant/abc123/order/789
    ```

    The request forwarded:

    ```URL
    https://api.myservice.com/clients/abc123/orders/789
    ```

    In this example, the values for `merchantId` and `orderId` are extracted from the public URL and injected into the proxy destination path.

    ***

    ###### Key Rules

    1. **Parameters must cover the entire path segment.** A parameter must replace the full segment between slashes. Partial segments are not supported.

       This will match:

    ```URL
        /merchant/{id}
    ```

    This will **not** match:

    ```URL
        /merchant-{id}
    ```

    2. **All parameters in the proxy URL must be defined in the public URL.** If a parameter is referenced in the proxy URL but not defined in the public URL, the connection creation will fail.

  </Tab>

  <Tab title="Wildcard Routing">
    ##### Wildcard Routing in Inbound Proxy

    Wildcard routing allows you to match a range of incoming request paths using a `*` at the end of the public URL. This is useful when you want a single route to handle multiple sub-paths under a common prefix.

    ###### How It Works

    A `*` can be appended at the end of the public URL path to capture any continuation of that path. The matched portion is then forwarded to the proxy URL.

    There are two ways to use wildcards depending on how strictly you want to match the prefix:

    ***

    **Using`prefix*`**

    Your public URL is:

    ```URL
    https://proxy.payrails.com/payments*
    ```

    Your proxy URL is:

    ```URL
    https://api.myservice.com/payments*
    ```

    This will match:

    ```URL
    https://proxy.payrails.com/payments
    https://proxy.payrails.com/payments/
    https://proxy.payrails.com/payments/checkout
    https://proxy.payrails.com/payments/refunds/123
    ```

    ***

    **Using`prefix/*`**

    Your public URL is:

    ```URL
    https://proxy.payrails.com/payments/*
    ```

    Your proxy URL is:

    ```URL
    https://api.myservice.com/payments/*
    ```

    This will match:

    ```URL
    https://proxy.payrails.com/payments/
    https://proxy.payrails.com/payments/checkout
    https://proxy.payrails.com/payments/refunds/123
    ```

    This will **not** match:

    ```URL
    https://proxy.payrails.com/payments
    ```

    ***

    ###### Key Rules

    1. **The`*` must appear only at the end of the path.** Wildcards in the middle of a path (e.g., `/payments/*/checkout`) are not supported.

    2. **A valid prefix is required before the`*`.** A standalone `*` or a path starting directly with `*` is not allowed.

    3. **`prefix*`vs`prefix/*`** — use `prefix*` when you also want to match the bare prefix without a trailing slash, and `prefix/*` when you want to match only paths that continue beyond the slash.

  </Tab>
</Tabs>

### Configuring Outbound Connections

In an outbound connection, you will use the [API endpoint](/reference/outboundconnectioninvocation#/) by specifying the connection to invoke a given connection. When you invoke this connection, you will specify in the request headers to which destination the request should be sent, and our system will check the trusted URL list that you configure in the connection.

### Configuring Proxy Rules

When sending a card to an external system or receiving from an external system, you must help us find the sensitive data you intend to extract or reveal from the HTTP request, how you want to replace it in your server, and how you want us to store it in our Vault.

For each rule, you configure where in the HTTP message the proxy should target, the operation (tokenize or detokenize) to be made, the type of record to be targeted in the HTTP message, and the path of the fields to be targeted during proxy.

##### **Operation target**

Is the sensitive information in the **Request body** or **Response body** of the interaction with the external system, or both? You can create separate rules if you have sensitive information in the HTTP call's request and response bodies.

##### **Operation type**

- **Tokenize**: If you want us to extract sensitive information, tokenize it in our Vault, and replace it with an alias when we forward the request to you.
- **Detokenize**: If you want us to reveal sensitive information currently stored in our Vault to the external system.

##### **Record type and selector**

In case if payload contains multiple records at once, you should specify the **record selector**.

You must indicate precisely where the Record is in the request or response body. The **selector** field follows the [JSONPath](https://www.rfc-editor.org/rfc/rfc9535.html) format if the body is JSON and [XPath](https://www.w3.org/TR/1999/REC-xpath-19991116/) format if it is XML.

For more information about Records and Fields, check here.

<Note>
  Currently, we support only **Card** or **Network token** as record types, and
  **JSON** and **XML** as content types. You can request new ones to our team if
  needed.
</Note>

##### **Field type and selector**

Depending on the record type you selected above, you will be asked to define details on each **Field** that composes the record.

Each field has:

- a **selector** that tells us where to find the field inside the HTTP message.
- the **regex** for parsing it if necessary. In most cases, the data that you want to tokenize or detokenize is returned by the selector, for example <card><expiryMonth>11</expiryMonth><expiryYear>29</expiryYear></card>. In some cases, your payload may contain multiple fields like <expiryDate>1129</expiryDate> or <expiryDate>11/29</expiryDate>. In such cases selector will return data like 1129, and you need to specify which part of it is the month and which one is the year.
  - If data does not require any special parsing, you should leave **regex** empty: in this case whole content of the element or attribute returned by **selector** will be used as value.
  - An example of input format 11/29, if you want to extract the month, you can use a regex that matches to month, for example /^\d{1,2}(?=/)/
  - You can go to the next section to learn more about how to parse fields with Regex (regular expressions).

Additionally, in the case that the proxy rule is configured for the operation type of 'tokenize':

- an **alias format** that indicates how to store it in our Vault. Typically, a random UUID. In case that you need a particular format, contact our support team so that we can enable it for you.
- a **display format** to choose how we display the tokenized data in a non-sensitive way, e.g., the last four digits of a card number, or the original value of an expiry date. Displayable formats are defined according to the PCI DSS standards and shown in the Portal for each field.
- a **replacement format** that allows choosing whether the tokenized value should be replaced with the alias or with the displayable value inside the transformed body received by the merchant. For example, an expiry date can be received either as a UUID alias or as its original value, which is its displayable format.
- a **storage policy** that indicates how long we should store the value for. Typically, permanent for the card data, except for its security code, which should be volatile to comply with PCI DSS policies.

#### Parsing Fields with Regex

Regex (regular expressions) allows you to specify a certain part of the fields to be picked for processing a rule inside the connection configuration. The regex gives you the capability to split one single field into multiple inputs.

For example, if the expiry date for a card comes in a single field instead of 2 separate fields, you can use a regex to split the field for tokenization. Let's take an example below:

```Text JSON
{
 "record":
    {
		"cardNumber": "4111111111111111",
		"expiryDate": "03/33"
    }
}
```

If you will receive a request where the expiryDate is passed as above, you should provide a regex in the connection configuration for expiry date fields in the following way:

| Field        | Configuration in the Proxy Rule | Value        |
| :----------- | :------------------------------ | :----------- |
| Expiry Month | Field selector                  | $.expiryDate |
| Expiry Month | Regex                           | (\d\d)/\d\d  |
| Expiry Year  | Field selector                  | $.expiryDate |
| Expiry Year  | Regex                           | \d\d/(\d\d)  |

Notice how the field selector for both fields is the same, but the regex for picking the value is different. In this case, our processing will pick the individual segments defined by the regex for processing and replace them back into their corresponding place in the original string.

The rules for parsing fields using regex are as follows:

- Must be written in Perl notation
- Must have only 1 group in the regex
- Must result in only 1 match in the regex

It is imperative that you ensure that the regex follows the above rules to ensure processing of the fields. Errors in regex can lead to unexpected behaviour.

**Behaviour of regex**

1. If the regex matches results in more than 1 group or more than 1 match, then we will be unable to pick the correct data from the field. This will result in the nullification of the field, and it will not be used for connection processing.
2. If there are collisions in the regex between fields (i.e., same regex used in 2 different selectors), we will attempt the processing for one of the fields but nullify the other.
3. If the regex is correct for the fields, then it will be used for processing and replaced in its original place. The original place is defined as the segment of the original group that got picked by the regex. The rest of the string is preserved as is.

**Recommended tools**

[Regex101](https://regex101.com/) with the Golang flavour will allow you to test the exact representation that is used by our platform for parsing regex.

Examples:

1. [Extracting the month from date](https://regex101.com/r/xXHr5d/1)
2. [Extract the year from date](https://regex101.com/r/7tBL4g/1)
3. [Extract a card from a complex string](https://regex101.com/r/rd2ybv/1)

#### Configuring Trusted hosts

When configuring outbound connections, you must specify a list of Trusted Hosts. This ensures that Payrails only forwards sensitive data to destinations you have explicitly authorized.

To support complex setups—such as aggregators managing multiple sub-merchants or hotels—Payrails supports Dynamic Host Patterns. This allows you to whitelist multiple subdomains using wildcards instead of listing every individual fully qualified domain name (FQDN).

**Host Types**

You can configure two types of host entries in your connection settings:

- **Static Host**: A fully qualified domain name that requires an exact match (e.g., `hotel-1.payments.com`).
- **Dynamic Host:** A pattern using wildcards (`*`) to match specific subdomain levels.

**Wildcard Matching Rules**

Payrails uses a segment-based matching logic. Each wildcard corresponds to exactly one subdomain level.

| Pattern            | Matches                    | Does NOT Match             |
| :----------------- | :------------------------- | :------------------------- |
| `hotel-1.com`      | `hotel-1.com`              | `api.hotel-1.com`          |
| `*.payments.com`   | `hotel-1.payments.com`     | `api.hotel-1.payments.com` |
| `*.*.payments.com` | `api.hotel-1.payments.com` | `hotel-1.payments.com`     |

**Implementation Guidelines**

When defining your patterns, keep the following validation rules in mind:

- **Domain Requirement**: Patterns must include a valid domain. Broad patterns like `*.com` or `*.co.uk` are not permitted.
- **Segment Integrity**: The wildcard _ must represent a full segment. Partial matches (e.g., `payments-_.processor.com`) are not supported.
- **Specific Subdomains**: Wildcards should only be used for the most specific (left-most) segments. Patterns like `payments.*.google.com` are invalid.

<Note>
  **Note**: This check is performed at the connection level. The same dynamic
  host patterns need to be whitelisted by Payrails support by providing adequate
  PCI AOC for the hosts to allow our vault to connect to these hosts.
</Note>

**Security Note: Subdomain Takeover**

Using broad wildcard patterns increases the risk of **Subdomain Takeover.** This occurs if a DNS entry points to a third-party service that has been decommissioned but not unclaimed. An attacker could claim that resource and, because the hostname still matches your wildcard, the Vault will permit the outbound request.

<Warning>
  **Important**: It is the merchant's responsibility to ensure that expired
  subdomains and third-party resources are cleaned up properly to prevent
  unauthorized data exfiltration.
</Warning>

## Step 3: Review configuration and make live

After defining the connection, we will take you to a Review page, where you can check the provided values before going live. After review, your connection version will be created but will not be live yet.

In order to make a version live, you will have to click on the version you want to make live on the versions page.

<Note>
  In order to get a connection version's details by using API, you can use our API endpoint [here](/reference/connectionversiondetail#/).

In order to make a connection live by using API, you should use the API endpoint [here](/reference/setliveversion#/) presented in our API reference.

</Note>

## Step 4: Manage connections

After creating your connections, you will be able to list, filter, and see all created versions of them in our Portal and via API endpoints.

You can simply select connections to see the details of the connection, the live version, and the inactive versions' details. You can change the live version anytime, or deactivate it. When editing, you can either start with an empty configuration or use an existing version and make changes to it if you don't want to start from scratch.

<Note>
  In order to list & filter connections by using API, you should use our API
  endpoint [here](/reference/listconnections#/) and for
  listing connection versions of a particular connection, use
  [here](/reference/listconnectionversions#/) in our
  API reference.
</Note>
